### rust2zig architecture details worth stealing (from README + design docs, 2026-08-11 state)

- **Pipeline**: `main.rs` (CLI, takes a Cargo package dir) → `scip.rs` (loads `index.scip` produced by `rust-analyzer scip .`; maps occurrence range → symbol, kind, signature) → `desugar/` (AST→AST passes on `syn::File`: `binary` inserts explicit derefs on `&T` operands, `match_ergonomics` makes binding modes explicit) → `analyze` (collects struct/enum/generic-fn tables keyed by SCIP symbol) → `translate/` (structural emission). The desugar passes are backend-neutral: "only target-specific lowerings (e.g. signed `%` -> `@rem`) stay in the translator" — which is why a second **OCaml backend** (`ml/` with dune projects) now shares the same front end.
- **Semantic queries**: `Scip::symbol_at`, `kind_at`, `type_at` (parses `signature_documentation.text`, e.g. `xs: &[i32]`, `self: &Option<T>` as `syn::Type`), and `binary_type_at` (reads the dispatched trait impl like `ops/arith/impl#[i32][`AddAssign<&i32>`]add_assign()` to recover operand types — this is how `total += *x` desugaring is made sound). Monomorphization: `GenericArgRef { arg, path }` locates the type-param instantiation at a call site (bare `T` → path `[]`, `Option<T>` → `[0]`, `HashMap<K,T>` → `[1]`).
- **Key mapping decisions**: generics → Zig comptime args; `&T` → `*const T`, `&mut T` → `*T`, `&[T]` → `[]const T`, `&self` → `self: *const Self`; lifetimes erased; shadowing handled by a `collect_renames` pass ("Zig rejects shadowing across all nested scopes; but siblings are independent"); Zig keywords escaped as `@"name"` (e.g. `Option::and` → `fn @"and"`); closures → `struct { ... fn call(...) }` instances with `.call` appended at call sites (type-driven via `is_closure_type` on `impl Fn` bounds, so closure-typed *parameters* work for free).
- **Test discipline**: `test.sh` = byte-for-byte golden files; `test_test.sh` = runs `cargo test` on each Rust example and `zig test` on the translated Zig file "to ensure the input/output pairs used to test the translator are in fact equivalent". Passing examples as of 2026-08: gcd, div, option (generic enum), sum, geometry (`&mut self`), closure, iter, dot (`std::iter::zip`), bitset, drop/drop2 (Drop elaboration), hash (FNV-1a from `const-fnv1a-hash`), random (PCG from `oorandom`), calc (`Result` + `?`). `coverage.md` + `redundancy.sh` track per-example coverage and flag retireable examples. **This is the most complete, testable Rust→Zig corpus in existence and the natural baseline/benchmark for our project.**
- **Known gaps** (its own "Bugs" section): union(enum) field/method name collisions need a renaming strategy; labeled blocks all emit `blk` (no unique labels); `println!("{}", x)` lacks type-driven format specifiers (currently "hacked with sed"); iterator `for` loops beyond ranges/arrays/slices/zip/enumerate are TODO; `&mut T` match scrutinees emit `*const` instead of `*T`.

## 2. Zig's translate-c (reference architecture — short)

Zig translates **C only**. There is no C++ and no Rust translator. Source: repo tree §1; docs:

> "Zig's C translation capability is available as a CLI tool via `zig translate-c`. It requires a single filename as an argument. It may also take a set of optional flags that are forwarded to clang. It writes the translated file to stdout."
> — https://ziglang.org/documentation/0.16.0/ (section "C Translation CLI")

Invocation facts (same doc): flags `-I`, `-D`, `-cflags [flags] --` (arbitrary clang flags), `-target`; docs warn "you must use the same `-target` triple that you will use when compiling the translated code" and matching `-cflags` or "you could result in clang or Zig parse failures, or subtle ABI incompatibilities". `@cImport` uses the same underlying machinery ("@cImport and zig translate-c use the same underlying C translation functionality, so on a technical level they are equivalent"), and C translation participates in the Zig cache (section "C Translation Caching", `--verbose-cimport`).

Output is deliberately non-idiomatic and expected to be hand-edited:

> "If you need to pass cflags to clang, or if you would like to edit the translated code, it is recommended to use `zig translate-c` and save the results to a file. Common reasons for editing the generated code include: changing `anytype` parameters in function-like macros to more specific types; changing `[*c]T` pointers to `[*]T` or `*T` pointers for improved type safety; and enabling or disabling runtime safety within specific functions."
> — https://ziglang.org/documentation/0.16.0/ (section "@cImport vs translate-c")

Architecture change in flight: translate-c is being ported from clang to **Aro**, Zig's own C parser. Issues #16268 ("upstream Aro and use it for translate-c instead of clang", closed 2023-06-29), #24497 ("compiler: update aro and translate-c to latest; delete clang translate-c", closed 2025-07-18), #20875 (open, 2024-07-30: "`zig cc`, `zig c++`, `zig translate-c` and other subcommands without a clang/llvm dependency in the compiler binary"). There are 483 issues matching "translate-c" in title; long tail of small correctness bugs (macros, typedef recursion, ternary operators, bitfields) shows translate-c itself is a perpetual maintenance surface.

Third-party evaluation of translate-c quality (zserge, 2022-07-06, translating the same BASIC interpreter with ccgo/c2rust/translate-c):

> "The code is much more readable than Go translation and follows not only the function structure, but also the structure of conditionals and loops. Even the variable names match C code most of the time." / "Zig would be the winner" for closeness to the original — though it failed on `memmove()` because "it is not part of the Zig C runtime yet".
> — https://zserge.com/posts/transpilers/

Deep internals of translate-c (Translator.zig, MacroTranslator.zig, span mapping, etc.) are out of scope for this file; they belong in parsing-tooling.md.

## 3. Analogous transpilers (source-verified)

### C→Rust: immunant/c2rust (the model to study)
- https://github.com/immunant/c2rust — 4,785 stars, active, requires "LLVM 15 or later with its corresponding clang compiler and libraries".
- Architecture: clang front end exported to Rust. "The c2rust-transpile library uses the c2rust-ast-exporter library to translate C code to Rust. The ast-exporter library links against the native clang compiler front end to parse C code and exports the AST for use in the transpiler, which is then implemented purely in Rust." — https://c2rust.com/manual/c2rust-transpile/index.html
- **Two-phase (now three-plus) pipeline** — the key lesson:
  > "The transpiler, `c2rust transpile`, produces unsafe Rust code that closely mirrors the input C code. The primary goal of the transpiler is to preserve functionality; test suites should continue to pass after translation. The output of `c2rust transpile` is unsafe and unidiomatic; it is merely the first step in a longer migration process." — https://github.com/immunant/c2rust (README)
  - Phase 2: `c2rust refactor` — deterministic cleanup via rustc internals ("uses `rustc` internal APIs... pinned to a specific `rustc` `nightly` version: `nightly-2023-04-15`").
  - Phase 3: `c2rust postprocess` — "an LLM-powered postprocessing tool for additional types of cleanup that are hard to do deterministically. Even though the postprocessor validates the output of LLMs, it can introduce errors; we recommend using it in combination with a robust test suite."
  - Cross-checking: "The transpiler can instrument the transpiled Rust code for cross-checking" (`-x, --cross-checks`) — runtime comparison against the original binary.
- Build integration: consumes `compile_commands.json`; `-e/--emit-build-files` emits cargo skeletons.

### C++→Rust: Cpp2Rust (academic, PLDI 2026)
- https://github.com/Cpp2Rust/cpp2rust — 292 stars, MIT, active; paper https://doi.org/10.1145/3808266 (Proc. ACM Program. Lang. 10, PLDI, Article 188, June 2026).
- Architecture (README): "Cpp2Rust first parses the input C++ file(s) with clang and produces an AST. It then traverses the AST and emits Rust code as strings, inserting calls to the `libcc2rs` runtime library where needed (e.g., for raw pointer semantics). Finally, the Rust code is pretty-printed using `rustfmt` to a single `.rs` file." Default **reference-counting model** for fully safe output; `--model=unsafe` for comparison.
- The fundamental mismatch is solved with a runtime: "C pointers are converted into the `Ptr<T>` type provided by `libcc2rs`. `Ptr<T>` models C pointer semantics, including null, arithmetic, and aliasing, while satisfying Rust's borrow checker through checked run-time operations."
- Evaluation (abstract): "inserting runtime-enforced ownership and mutability checks, ensuring safety while preserving semantics... full memory safety with only a 2% performance penalty on WOFF2 compression, while being 6× slower on Brunsli due to heavy usage of pointer arithmetic."
- Translation rules are expressed as a rule/plugin system (`translation_rule.cpp`, `plugins/emplace_back.cpp`) plus macro-generated state machines for C++ control flow (`libcc2rs-macros`: goto, switch, state_machine).

### C++→Zig: lassade/c2z (bindings + partial transpile)
- https://github.com/lassade/c2z — 126 stars, 2023-06-08 → 2025-04-06 (dormant ~16 months), C++ implementation.
- Approach: "`zig cc -x c++ -std=c++11 -Xclang -ast-dump=json {input_file}`" — dumps the clang AST as JSON and translates that; inspired by floooh's sokol-bindgen article (https://floooh.github.io/2020/08/23/sokol-bindgen.html).
- Honest limitations in its own README: "Glue is invitable ... snap ... and needed to make the bindings cross platform"; "Transpiled code can leak memory (implicit destructors aren't called)"; "Manual adjustments are required, specially to make bindings idiomatic and easer to read"; "Meant to work with libraries that follow the *C with classes* coding style". Test-suite coverage of real libs: fpng 99.99%, xatlas 86.40%, imgui 67.21%.
- Takeaway: C++→Zig is so hard that even a working clang-AST-JSON pipeline settles for bindings + glue and explicitly disclaims idiomatic output and destructor semantics.

### C++→Zig community position (ziggit)
- Thread "C++ to Zig?" (https://ziggit.dev/t/c-to-zig/9197, 2025-03-21, 3 posts):
  > "Being able to compile C++ to Zig would basically require implementing C++ in Zig, which I doubt anyone would want to take on." — tensorush
  > "You could compile C++ to WASM via `zig c++`, then translate the WASM to C via wasm2c..., then translate the C output to Zig via `zig translate-c`. But even if that works the resulting Zig (and C) code will have absolutely nothing in common with the original C++ code" — floooh
- The community default position: no C++→Zig transpiler exists and none is expected. The closest practical path goes through WASM/C and loses all structure.

### C→Go: modernc.org ccgo (and the general pattern)
- https://zserge.com/posts/transpilers/ (2022-07-06): ccgo "is built on top of a custom C lexer/parser and AST walker that runs in multiple phases to convert C AST to Go code. For libc features it uses a custom library — modernc.org/libc — as well as the similar project for the CRT (C runtime). These libs become the hard dependencies of the generated code." Output: "barely readable - all is wrapped into `unsafe.Pointer` casting and spiced up with `goto`" and it crashed on unimplemented libc (`Xputs: TODOTODO`).
- Lesson: a **libc/runtime substitute is a hard dependency** of any C-family transpiler; the same will be true of std/allocator mapping for Rust→Zig.

### Rust→C: two tiny projects, both dead
- https://github.com/jasiukiewicztymon/rust2c — "Translate Rust code to C / C++", created and abandoned 2023-06-08 (one day), 3 stars, README is a title only.
- https://github.com/louy2/rust2c-llvm-cbe — 2 stars, 2021; the LLVM C-backend route (rustc → LLVM IR → C via `llvm-cbe`).
- Lesson: Rust→C has the same semantic-gap problems as Rust→Zig (ownership, Drop, generics, async) and no sustained project solved them.

### Go→Rust: all demos/abandoned
- tylerlaprade/go2rust (2025-07 → 2026-07, 9 stars, "The last Go program you'll ever need!"); johnpmayer/go2rust (2015, 1 star, demo); kazunari-kamata/go2rust-cli (2026, "Go ソースコードを Rust ソースコードの雛形へ変換する... 未対応構文は TODO コメントとして出力" — emits **TODO comments for unsupported syntax**, i.e., a partial translator that acknowledges incompleteness in-band).
- Lesson: even Go (simpler than Rust: GC, no borrowck, structural typing) never got a working Go→Rust transpiler. Successful migration paths are FFI (rust2go: https://news.ycombinator.com/item?id=41117749) or manual rewrite.

### TypeScript→Rust: a graveyard (same pattern as Rust→Zig)
- All abandoned/experimental: octaltree/betterty (2021, 6★), vedantroy/ts2rust (2020, 1★), coltonoscopy/ts2rust (2024, 2★), DanielleHuisman/typescript-transpiler (2024, 0★, "Exploratory project, there is probably no intention to finish it"), Kianse/tsrust-transpiler (2026, 0★).
- Lesson: the "translate a GC/managed-language to Rust" space is littered with tokenizer-and-AST demos. Sustained success requires semantic analysis + tests + a narrow target.

### Reverse direction, both flagships: Bun (Zig→Rust) and Roc (Rust→Zig)
These are the strongest evidence about what a Rust→Zig port actually entails, since they are the two largest real migrations in either direction.

- **Bun (Zig→Rust, 11 days, LLM-driven)**: https://bun.com/blog/bun-in-rust (2026-07-08). "Excluding comments, Bun is 535,496 lines of Zig." Strategy was explicitly a mechanical port: "Do the rewrite that looks like we transpiled our Zig code to Rust. We can gradually refactor it to reduce `unsafe` usage and look more like idiomatic Rust after Bun v1.4 ships." Driven by a `PORTING.md` (Zig→Rust pattern map) and a `LIFETIMES.tsv` (per-struct-field lifetime analysis), ~64 Claude agents, 6,778 commits, 0 tests skipped (test suite is language-independent TypeScript with ~1.4M assertions). Cost: 5.9B input tokens / 690M output tokens / ~$165K. Result: ~4% of code in `unsafe` (~13,000 keywords), 19 known regressions, most from "code that's syntactically identical in both languages but semantically different" — e.g. Zig `assert` is a function (argument always evaluated) vs Rust `debug_assert!` macro (argument erased in release); `ReleaseFast` removes bounds checks where Rust keeps them; `comptime` format strings rewrite markers before substitution vs Rust runtime `format_args!`.
- **Andrew Kelley on Bun's rewrite** (2026-07-09): https://andrewkelley.me/post/my-thoughts-bun-rust-rewrite.html — mostly relationship history; relevant facts: the Zig compiler is ~600,000 lines with "16s to build from scratch with a clean cache, followed by 90ms for each subsequent edit with incremental compilation"; Bun's comptime abuse and missing fuzzing were the substantive complaints. (Not a transpiler lesson per se, but context on why teams move between the two languages.)
- **Roc (Rust→Zig, manual rewrite)**: https://rtfeldman.com/rust-to-zig (2026-07-16). 300K lines of Rust → Zig in 487 days; table of real outcomes: Rust compiler had 21 memory-corruption bug reports (all miscompilations, none in compiler logic), Zig one had 10 (8 miscompilations + 2 real UAFs in error reporting that "Rust's borrow checker would have caught"). Motivation included allocator-model mismatch and pervasive unsafe; consequence: "Zig's ecosystem consistently passes around allocators, which is exactly what we want, whereas off-the-shelf Rust crates almost always assume a single global allocator." Also: Zig `-fincremental` rebuild of ~450K lines: ~35ms (on stable 0.16.0 it had a bug; fixed in 0.17.0).

## 4. Lessons for our project (each tied to a cited source)

1. **Semantic information is not optional; syntax-only tools die.** Every surviving translator is built on a real front end with type info: c2rust links clang's front end; Cpp2Rust and c2z consume clang AST (AST dump JSON in c2z's case); rust2zig pulls rust-analyzer SCIP dumps because `syn` alone cannot resolve binary-operator dispatch, match ergonomics, or monomorphization (README: "Use SCIP for semantic information"). The dead projects (ziggy, most TS→Rust, go2rust demos) all stop at hand-rolled tokenizers. For Rust→Zig the realistic semantic sources are rust-analyzer (SCIP, as rust2zig proves) or rustc's own query interface (as c2rust uses rustc internals for refactoring). [c2rust README; Cpp2Rust README; c2z README; rust2zig README]

2. **Plan a two-phase pipeline: mechanical translation first, refactoring second.** c2rust is the canonical proof: "The output of `c2rust transpile` is unsafe and unidiomatic; it is merely the first step in a longer migration process," followed by deterministic `c2rust refactor` and LLM `c2rust postprocess`. Bun independently chose the same shape ("Do the rewrite that looks like we transpiled... gradually refactor it"). c2z says "Manual adjustments are required, specially to make bindings idiomatic". Our deliverable should define what "idiomatic Zig" means and budget for a cleanup phase rather than demanding idiomatic output from the first pass. [immunant/c2rust README; bun.com/blog/bun-in-rust; lassade/c2z README]

3. **A runtime/support library will be needed for semantic gaps; plan its shape now.** Cpp2Rust inserts `libcc2rs` (`Ptr<T>` with "checked run-time operations") for C pointer semantics; ccgo depends on `modernc.org/libc` and broke on an unimplemented `puts`; translate-c output depends on Zig's C runtime (zserge hit a missing `memmove`). For Rust→Zig the mapped gaps are already enumerated by rust2zig's design docs: `Drop` → `defer`/alive-flag elaboration (design/drop.md: "Prefer idiomatic Zig: `defer x.drop()` when destruction is unconditional on scope exit; alive flags only when destruction is path-sensitive"), `Result`/`?` → error unions, `String` → slices+allocator, `Cell` → `*T`/atomic, generics → comptime. The allocator mismatch (Roc: Rust assumes a global allocator, Zig demands explicit allocators) means the translator must decide an allocator-threading strategy — this is a design decision no existing tool has solved. [Cpp2Rust README + abstract; zserge.com/posts/transpilers/; rust2zig design/drop.md; rtfeldman.com/rust-to-zig]

4. **Identical-looking syntax with different semantics is the main correctness trap; verify behaviorally, not by text.** Bun's 19 regressions "came from code that's syntactically identical in both languages but semantically different": Zig `assert` evaluates its argument in all builds vs Rust `debug_assert!` erases it in release; `ReleaseFast` drops bounds checks vs Rust keeps them; `comptime` format strings vs runtime format_args. Rust→Zig has the mirrored hazards: integer overflow (Rust panics on overflow in debug, wraps in release; Zig has explicit `+%`), `panic!` vs error returns, slice bounds under ReleaseSafe/ReleaseFast, `?`/`try` placement, `assert` vs `std.debug.assert` evaluation, and Drop timing. rust2zig's own test discipline is the model: golden-file comparison **plus** running `zig test` on the output and `cargo test` on the input ("test_test.sh runs `cargo test` on each Rust example and `zig test` on the corresponding translated Zig file. This ensures the input/output pairs used to test the translator are in fact equivalent"). c2rust's `--cross-checks` instrumentation is the same idea for C. Differential/behavioral testing is non-negotiable. [bun.com/blog/bun-in-rust; rust2zig README testing section; c2rust.com/manual/c2rust-transpile/index.html]

5. **Target a bounded dialect; whole-language ambitions die.** c2z explicitly scopes to "libraries that follow the *C with classes* coding style"; Cpp2Rust was evaluated on two specific libraries (WOFF2, Brunsli); rust2zig has a fixed example corpus with known TODOs ("For loops over iterators (other than ranges, arrays, slices, zip, and enumerate) are TODO") and known bugs ("Union field/method name collision... Needs a renaming strategy"); go2rust-cli emits `TODO` comments in-band for unsupported syntax. The pattern of failure is universal: tokenizer+AWP (all-languages) attempts die in weeks. Our project should pick a crate subset (e.g. `no_std`-ish, no async, no procedural macros) and be explicit about the dialect boundary. [lassade/c2z README; Cpp2Rust abstract; rust2zig README; kazunari-kamata/go2rust-cli]

6. **Macros are a front-end problem, not a back-end one — decide how to expand them.** C++→Rust work treats `goto`/switch/state-machines via macro-generated code (libcc2rs-macros); c2rust handles C macros via `-e`-style expansion plus `anytype`-parameter cleanup in translate-c output (Zig docs recommend editing function-like macro parameters manually). Rust's `macro_rules!`, derive macros, and proc macros are a much bigger expansion surface than C's preprocessor; rust2zig side-steps it by translating only hand-written examples (its `mac.rs` handles just `assert_eq!`, `panic!`, `println!`). A Rust→Zig tool must decide: expand via rustc (cargo expand), or restrict the input to macro-free code. This is a scoping decision with no prior art resolved. [Cpp2Rust repo structure; ziglang.org/documentation/0.16.0/@cImport-vs-translate-c; rust2zig src/translate/mac.rs]

7. **Build integration and verification tooling decide whether the output is usable.** c2rust consumes `compile_commands.json` and emits cargo skeletons; translate-c is exposed both as a CLI and as a `Build.Step.TranslateC` and participates in the Zig cache; c2z is invoked through `zig build run`. Bun's rewrite was only reviewable because "A language-independent test suite with a million assertions" existed. For our project: input is a Cargo package (rust2zig's CLI already "takes Cargo package directory as argument" and reads `index.scip` generated by `rust-analyzer scip .`); output must slot into `build.zig` with the same `-target`/`-cflags` discipline translate-c demands. [c2rust manual; ziglang.org/documentation/0.16.0 C-Translation-CLI + C-Translation-Caching; rust2zig README; bun.com/blog/bun-in-rust]

8. **Ownership/lifetime translation is THE hard problem, and it's asymmetric.** C++→Rust adds checks (Cpp2Rust: "addresses the fundamental mismatch between C++'s unrestricted aliasing and Rust's ownership model by inserting runtime-enforced ownership and mutability checks"). Rust→Zig removes guarantees: rust2zig "erases lifetimes" and maps `&T` to `*const T` — the safety that the borrow checker enforced is gone, and Zig's runtime checks (ReleaseSafe) only partially substitute (Roc: Zig's checks "are less comprehensive" than Rust's safe subset). The translator must decide how much of ownership to preserve: strict `*const`/`*` with careful aliasing rules, or per-value `defer`-based RAII emulation (rust2zig's drop elaboration). No prior work resolves this; it is a genuine design axis. [Cpp2Rust abstract; rust2zig README + design/drop.md; rtfeldman.com/rust-to-zig]

9. **LLM-driven porting is now a proven alternative that changes the value proposition of a deterministic transpiler.** Bun's 11-day, $165K, 64-agent port with `PORTING.md`/`LIFETIMES.tsv` pattern maps is the existence proof; c2rust's own roadmap already includes an "LLM-powered postprocessing tool". A deterministic Rust→Zig transpiler's best role may be (a) the structured first pass that an LLM workflow would otherwise improvise, or (b) the verifier/oracle (differential testing) for LLM output. The design phase should explicitly position the tool against this alternative rather than assume "translate → done". [bun.com/blog/bun-in-rust; immunant/c2rust README]

10. **Expect a maintenance treadmill around the front end.** translate-c has 483 open+closed issues and is being re-based from clang onto Aro (Zig's own parser) precisely to reduce that burden; c2rust pins a nightly rustc for its refactor tool; rust2zig re-imports `index.scip` from rust-analyzer per example. Any Rust→Zig tool inherits churn from both rustc/rust-analyzer (input side) and Zig language changes (output side; Zig 0.16 → 0.17 is currently breaking — Roc had to wait for the stable to use `-fincremental`). Budget for re-baselining against both ecosystems. [ziglang/zig #16268, #24497; c2rust README; rust2zig README build_index.sh; rtfeldman.com/rust-to-zig]

## 5. Open questions for the user (design-phase inputs)

1. **Semantic source: rust-analyzer SCIP (as rust2zig proves) or rustc's own query system?** SCIP is dependency-light but lossy (no trait solving beyond what rust-analyzer records; rust2zig's README notes `binary_type_at` only works for variable/parameter idents); rustc internals give full MIR/type info but pin us to a nightly (c2rust's pain). Which is acceptable?
2. **Scope dialect: does the target include async/await, procedural/derive macros, and generics-heavy crates like those using `serde`?** rust2zig already translates generics→comptime but has no async story; every successful predecessor scoped tightly. What crates must actually translate end-to-end for v1?
3. **Positioning vs LLM porting: is the tool a deterministic translator, a differential-testing oracle for LLM output, or a structured first pass feeding a refactor phase?** Bun proved LLMs can do a mechanical port with a pattern map; c2rust already layers LLM postprocessing on its deterministic transpiler. The architecture and the acceptance criteria differ substantially across these three roles.
